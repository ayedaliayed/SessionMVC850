Building the Edit Employee Form — 4 Ways

SessionMVC850 · ASP.NET Core MVC · English guide

What this guide covers The same Edit Employee page, written in four different styles: normal HTML, loosely typed HTML helpers, strongly typed HTML helpers, and tag helpers (asp-for, asp-action). For each style you will see the code, what it produces, its benefits, and its problems.

The form has five fields — Name, Age, Image, Phone, Department — plus a hidden Id. It posts to /Employee/SaveEdit, and the Cancel button goes back to /Employee.

1) Normal HTML — start here

How it works

You write plain HTML. The only rule that matters for MVC is the name attribute: it must match the model property so that model binding can fill Employee when the form is posted.

@model SessionMVC850.Models.Employee

@{
    ViewData["Title"] = "Edit Employee";
}

<h2>Edit Employee</h2>

<form action="/Employee/SaveEdit" method="post">
    <input type="hidden" name="Id" value="@Model.Id" />

    <div class="mb-3">
        <label for="Name">Employee Name</label>
        <input type="text" id="Name" name="Name" class="form-control"
               placeholder="Enter employee name" value="@Model.Name" />
    </div>

    <div class="mb-3">
        <label for="age">Age</label>
        <input type="number" id="age" name="age" class="form-control"
               placeholder="Enter age" value="@Model.age" />
    </div>

    <div class="mb-3">
        <label for="Image">Image</label>
        <input type="text" id="Image" name="Image" class="form-control"
               placeholder="Enter image path" value="@Model.Image" />
    </div>

    <div class="mb-3">
        <label for="Phone">Phone</label>
        <input type="text" id="Phone" name="Phone" class="form-control"
               placeholder="Enter phone number" value="@Model.Phone" />
    </div>

    <div class="mb-3">
        <label for="DeptId">Department</label>
        <select id="DeptId" name="DeptId" class="form-control">
            @foreach (var department in (IEnumerable<Department>)ViewBag.Departments)
            {
                if (department.Id == Model.DeptId)
                {
                    <option value="@department.Id" selected>@department.Name</option>
                }
                else
                {
                    <option value="@department.Id">@department.Name</option>
                }
            }
        </select>
    </div>

    <button type="submit" class="btn btn-primary">Save Changes</button>
    <a href="/Employee" class="btn btn-secondary">Cancel</a>
</form>

What gets generated

<input type="text" id="Name" name="Name" class="form-control"
       placeholder="Enter employee name" value="ali" />
Benefits
  • Easy to read and understand, especially for beginners.
  • Full control over every attribute and every pixel of markup.
  • No hidden magic — what you write is what the browser receives.
  • Works even if you later move away from ASP.NET Core MVC.
Problems
  • Magic strings: name="Name" and name="DeptId" are not checked by the compiler. A typo breaks model binding silently.
  • Hard-coded URLs: action="/Employee/SaveEdit" breaks if the route changes or the app runs under a path base.
  • No automatic validation: you must write validation attributes and messages yourself.
  • Manual selected option: the if/else for selected must be repeated for every dropdown.
  • Duplication: every field repeats the same wrapper and class names.
  • Refactoring is unsafe: renaming Employee.Name does not update name="Name".

2) Loosely typed HTML Helpers

How it works

Instead of writing tags, you call helpers such as Html.TextBox, Html.Label, Html.DropDownList and pass the property name as a string. The helper generates the HTML for you.

@model SessionMVC850.Models.Employee

@{
    ViewData["Title"] = "Edit Employee";
}

<h2>Edit Employee</h2>

@using (Html.BeginForm("SaveEdit", "Employee", FormMethod.Post))
{
    @Html.Hidden("Id", Model.Id)

    <div class="mb-3">
        @Html.Label("Name", "Employee Name")
        @Html.TextBox("Name", Model.Name, new { @class = "form-control", placeholder = "Enter employee name" })
    </div>

    <div class="mb-3">
        @Html.Label("age", "Age")
        @Html.TextBox("age", Model.age, new { @class = "form-control", type = "number", placeholder = "Enter age" })
    </div>

    <div class="mb-3">
        @Html.Label("Image", "Image")
        @Html.TextBox("Image", Model.Image, new { @class = "form-control", placeholder = "Enter image path" })
    </div>

    <div class="mb-3">
        @Html.Label("Phone", "Phone")
        @Html.TextBox("Phone", Model.Phone, new { @class = "form-control", placeholder = "Enter phone number" })
    </div>

    <div class="mb-3">
        @Html.Label("DeptId", "Department")
        @Html.DropDownList("DeptId",
            new SelectList((IEnumerable<Department>)ViewBag.Departments,
                           "Id", "Name", Model.DeptId),
            new { @class = "form-control" })
    </div>

    <button type="submit" class="btn btn-primary">Save Changes</button>
    @Html.ActionLink("Cancel", "Index", "Employee", null, new { @class = "btn btn-secondary" })
}
Important details Html.BeginForm("SaveEdit", "Employee", FormMethod.Post) builds the form URL from routing instead of hard-coding it. SelectList takes the data source, the value field (Id), the text field (Name) and the selected value (Model.DeptId).

What gets generated

<input type="text" id="Name" name="Name" class="form-control"
       placeholder="Enter employee name" value="ali" />
Benefits
  • Less markup than writing every tag by hand.
  • The helper generates a correct id and name from the string.
  • BeginForm and ActionLink generate URLs from the route table.
  • Useful when the property name is dynamic (built at runtime) and cannot be written as a lambda expression.
Problems
  • Still magic strings: "Name" and "DeptId" are not checked by the compiler or IntelliSense.
  • Typos cause silent bugs: Html.TextBox("Nmae", ...) renders an input that never binds to the model.
  • Refactoring breaks: renaming a property does not update the string.
  • No compile-time support for model changes; errors appear only at runtime.
  • Many overloads are confusing, and it is easy to pass arguments in the wrong order.
  • Validation attributes are not guaranteed; you must add validation messages manually.

3) Strongly typed HTML Helpers

How it works

You pass a lambda expression (m => m.Name) instead of a string. The compiler checks the property, IntelliSense helps you choose it, and renaming a property updates the helper automatically.

@model SessionMVC850.Models.Employee

@{
    ViewData["Title"] = "Edit Employee";
}

<h2>Edit Employee</h2>

@using (Html.BeginForm("SaveEdit", "Employee", FormMethod.Post))
{
    @Html.HiddenFor(m => m.Id)

    <div class="mb-3">
        @Html.LabelFor(m => m.Name, "Employee Name")
        @Html.TextBoxFor(m => m.Name, new { @class = "form-control", placeholder = "Enter employee name" })
        @Html.ValidationMessageFor(m => m.Name, "", new { @class = "text-danger" })
    </div>

    <div class="mb-3">
        @Html.LabelFor(m => m.age, "Age")
        @Html.TextBoxFor(m => m.age, new { @class = "form-control", type = "number", placeholder = "Enter age" })
    </div>

    <div class="mb-3">
        @Html.LabelFor(m => m.Image, "Image")
        @Html.TextBoxFor(m => m.Image, new { @class = "form-control", placeholder = "Enter image path" })
    </div>

    <div class="mb-3">
        @Html.LabelFor(m => m.Phone, "Phone")
        @Html.TextBoxFor(m => m.Phone, new { @class = "form-control", placeholder = "Enter phone number" })
    </div>

    <div class="mb-3">
        @Html.LabelFor(m => m.DeptId, "Department")
        @Html.DropDownListFor(m => m.DeptId,
            new SelectList((IEnumerable<Department>)ViewBag.Departments, "Id", "Name"),
            new { @class = "form-control" })
    </div>

    <button type="submit" class="btn btn-primary">Save Changes</button>
    @Html.ActionLink("Cancel", "Index", "Employee", null, new { @class = "btn btn-secondary" })
}
EditorFor instead of TextBoxFor You can replace @Html.TextBoxFor(m => m.Name, ...) with @Html.EditorFor(m => m.Name, new { htmlAttributes = new { @class = "form-control" } }). EditorFor chooses the editor from the property type and data annotations, but it may add extra wrapper markup.

What gets generated

<input type="text" id="Name" name="Name" class="form-control"
       placeholder="Enter employee name" value="ali"
       data-val="true" data-val-required="The Name field is required." />
Benefits
  • Compile-time checking: a wrong property name is a build error, not a silent runtime bug.
  • IntelliSense lists the model properties as you type.
  • Safe refactoring: renaming a property updates all For helpers.
  • Uses model metadata (data annotations) to generate labels and validation attributes.
  • DropDownListFor automatically selects the current DeptId.
Problems
  • More verbose syntax: every field needs a lambda expression.
  • You still write markup through method calls and anonymous objects, which can become hard to read.
  • Less control over exact HTML than plain tags, and EditorFor can add wrapper elements.
  • DropDownListFor needs a SelectList and a ViewBag/model property for the items.
  • Not ideal for very complex or highly custom layouts.

4) Tag Helpers — asp-for and asp-action

How it works

Tag helpers let you keep normal-looking HTML tags, then add asp-* attributes. MVC processes them on the server and writes the correct HTML.

Prerequisite Tag helpers must be registered. Make sure Views/_ViewImports.cshtml contains: 
@addTagHelper *, Microsoft.AspNetCore.Mvc.TagHelpers
@model SessionMVC850.Models.Employee

@{
    ViewData["Title"] = "Edit Employee";
}

<h2>Edit Employee</h2>

<form asp-controller="Employee" asp-action="SaveEdit" method="post">

    <input type="hidden" asp-for="Id" />

    <div class="mb-3">
        <label asp-for="Name" class="form-label">Employee Name</label>
        <input asp-for="Name" class="form-control" placeholder="Enter employee name" />
        <span asp-validation-for="Name" class="text-danger"></span>
    </div>

    <div class="mb-3">
        <label asp-for="age" class="form-label">Age</label>
        <input asp-for="age" class="form-control" type="number" placeholder="Enter age" />
    </div>

    <div class="mb-3">
        <label asp-for="Image" class="form-label">Image</label>
        <input asp-for="Image" class="form-control" placeholder="Enter image path" />
    </div>

    <div class="mb-3">
        <label asp-for="Phone" class="form-label">Phone</label>
        <input asp-for="Phone" class="form-control" placeholder="Enter phone number" />
    </div>

    <div class="mb-3">
        <label asp-for="DeptId" class="form-label">Department</label>
        <select asp-for="DeptId" class="form-control"
                asp-items="@(new SelectList((IEnumerable<Department>)ViewBag.Departments, "Id", "Name"))">
        </select>
    </div>

    <button type="submit" class="btn btn-primary">Save Changes</button>
    <a asp-controller="Employee" asp-action="Index" class="btn btn-secondary">Cancel</a>
</form>

@section Scripts {
    <partial name="_ValidationScriptsPartial" />
}

What each asp-* attribute does

AttributePurpose
asp-for Strongly typed binding: generates id, name, value, and validation attributes from the model property.
asp-validation-for Shows the validation message for one property.
asp-action Generates the URL of an action using routing (no hard-coded path).
asp-controller Chooses the controller for asp-action. Optional when it is the current controller.
asp-items Fills a <select> with options from a SelectList.
asp-route-id Adds a route value (used on links, for example asp-action="Details" asp-route-id="@item.Id").
Why asp-for + asp-items is better than the manual dropdown asp-for="DeptId" automatically marks the option whose value equals Model.DeptId as selected. You no longer need the if/else and the selected attribute.

What gets generated

<form action="/Employee/SaveEdit" method="post">
...
<input type="text" id="Name" name="Name" class="form-control"
       placeholder="Enter employee name" value="ali"
       data-val="true" data-val-required="The Name field is required." />
...
</form>
Client-side validation The example ends with a @section Scripts block that renders _ValidationScriptsPartial. That partial loads jQuery validation, so asp-validation-for shows messages in the browser without a page reload.
Benefits
  • Clean HTML: markup looks like normal HTML, so designers can read it.
  • Strongly typed: asp-for is checked by the compiler and IntelliSense.
  • Safe URLs: asp-action and asp-controller generate links from routing instead of hard-coded strings.
  • Automatic selected option in dropdowns through asp-for + asp-items.
  • Automatic validation attributes and messages.
  • Less code than strongly typed helpers and easier to read.
Problems
  • Requires @addTagHelper registration; without it the asp-* attributes are ignored and the form breaks silently.
  • The HTML looks static, so beginners may not realize the server is processing it.
  • asp-items expects a SelectList / IEnumerable<SelectListItem>, which needs an explicit cast with ViewBag.
  • Some advanced scenarios still need HTML helpers (for example custom editor templates).
  • You must run the app to see the generated HTML; the source alone is not the final output.

5) Comparison: benefits and problems

Feature Normal HTML Loose helpers Strong helpers Tag helpers
Compile-time checking No No (strings) Yes Yes
IntelliSense for properties No No Yes Yes
Safe refactoring No No Yes Yes
Automatic id / name Manual Yes Yes Yes
URL generation from routing Manual BeginForm / ActionLink BeginForm / ActionLink asp-action / asp-controller
Automatic validation attributes Manual Limited Yes Yes
Automatic selected dropdown option Manual if/else Pass selected value Yes Yes
Control over exact HTML Full Medium Low–medium High
Verbosity High Medium High Low
Learning curve Low Medium Medium Low–medium
Summary Normal HTML is the easiest to learn but the least safe. Loosely typed helpers reduce markup but still use unchecked strings. Strongly typed helpers are safe but verbose. Tag helpers give you safe binding with the cleanest HTML.

6) Problems in the current file

The pasted Edit.cshtml mixes several approaches at once, which causes duplicated fields and confusing behavior:

ProblemWhy it is a problemFix
@ViewData["Title"] before @model Razor directives should start the file with @model first. Put @model SessionMVC850.Models.Employee on line 1.
ViewData["Title"] declared twice Redundant and confusing. Keep only one @{ ViewData["Title"] = "Edit Employee"; } block.
Five controls all named Name / Id="Name" EditorFor, LabelFor, asp-for label, TextBoxFor and TextBox("Name") all render at once. Duplicate id values are invalid and the posted value is unpredictable. Choose one approach and keep one input per field.
Html.TextBox("Name", null, placeholder = "Enter age") The name is Name but the placeholder says “age”; it also duplicates the Name input. Use Html.TextBox("age", Model.age, ...) or, better, <input asp-for="age" ... />.
Hard-coded action="/Employee/SaveEdit" Breaks if routing or the path base changes. Use asp-action="SaveEdit" asp-controller="Employee" or Html.BeginForm.
No validation messages The user gets no feedback when a field is invalid. Add <span asp-validation-for="Name"></span> or @Html.ValidationMessageFor(...).
Manual selected logic for the dropdown Works, but it is repetitive and easy to forget. Use <select asp-for="DeptId" asp-items="...">.

7) Which one should you use?

Recommendation
  • Learn with normal HTML first — it teaches model binding and the name attribute, which is the foundation of everything else.
  • Use tag helpers for real forms — asp-for, asp-items, asp-action and asp-controller give you safety and clean markup.
  • Use strongly typed helpers when you need a helper method, a custom editor template, or code that is easier to generate dynamically.
  • Use loosely typed helpers only when the property name is truly dynamic; otherwise they are the weakest choice.
  • Use normal HTML for static content, or when you need exact markup that no helper can produce.

To switch the project's page to the recommended version, replace the body of Views/Employee/Edit.cshtml with the tag helper example from section 4. The controller action and the EmployeeBL.Update method do not need any change: they still receive the same Employee object.
